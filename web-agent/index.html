Results

The same agent, the same 36 tasks, run twice: once with the recovery half of its loop switched on, once with it switched off.

Twenty-seven of the tasks are controls — forms, tables, wizards, business workflows and portal navigation that a competent agent should pass either way. Nine are adversarial: the page mutates or obstructs mid-task — a button is renamed after a field is typed into, an overlay rises over the control, a same-label decoy appears. Every number on this page is computed from the raw run files of that evaluation (results/run_on.json and results/run_off.json); nothing is hand-entered.

Method

The agent drives headless Chromium (Playwright) through the task suite. Each task is a sequence of steps, and every step carries an explicit postcondition written against the page. For each step the agent runs one loop:

Observe and ground

Observe takes a fresh DOM snapshot: every interactive element with a reference, role, text, id, name, label, form and visibility. Ground matches the step’s semantic target — role plus text, label or name — against that snapshot. Act clicks, fills, selects or checks via the element’s locator recipe. Verify checks the step’s postcondition: visible text, row counts, field values, checked state.

Recover — re-grounding

When a step fails — target not found, an action error, or a postcondition not met — recovery first re-grounds: the target is looked up again in a fresh snapshot with fallback strategies instead of the exact text or id — for example the submit control of the named form, or the only visible element of that role in scope. That is what survives a button being renamed mid-task (“Pay now” → “Confirm payment”, new id) or moved in the page.

Recover — overlay dismissal and the retry budget

If the click error says another element intercepts pointer events, the agent finds the overlay’s dismiss control (Accept / Close / ×), clicks it, and retries. Retries are budgeted — at most 2 per step — then the task fails and the failure is reported as-is. Every observe, failure and recovery is written to the run log.

The ablation

Recovery off disables all three mechanisms: no re-grounding, no overlay dismissal, no retries — the first failure ends the task. The evaluation runs the identical suite in both modes, so the difference between the two columns on this page is the measured worth of the recovery half of the loop.

Scope, stated plainly

The evaluation runs against deterministic local fixture pages in headless Chromium — pages styled as real product surfaces (a CRM portal, a store checkout, settings and admin flows) rather than bare HTML. The live session operates the same pages. Seven adversarial tasks needed exactly one recovery with recovery on; the two double-mutation tasks needed two.

How to use

1 · Pick a task

Choose one of the 36 fixture tasks — a form, a checkout, a CRM or portal flow, or one of the nine adversarial tasks where the page mutates mid-task. In the live session you can also point the agent at a public page.

2 · Toggle recovery

Run the task with recovery on, then switch recovery off and run the same task again. Recovery off disables re-grounding, overlay dismissal and retries — the first failure ends the task.

3 · Read the results panel and the trace

The results panel reports pass or fail against the task's step postconditions, with attempts and recoveries counted. The trace shows every step as it happens — observe, ground, act, verify, and each recovery — with screenshots along the way.
